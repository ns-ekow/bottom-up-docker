bottom-up-docker

Docker from the kernel up. Build each layer yourself, then read and trace the production code that does the same job.
See the curriculumSet up the labHow this course works

Observe

Every concept is first seen on a real kernel in a disposable lab VM, with stock tools only.

Build

Then you implement it in Go. Over the course, those pieces become bud, a working container engine.

Read and trace

Then you read the real code (runc, containerd, moby, BuildKit, Linux) pinned to one frozen release, and watch it run.

Cited

Every factual claim links to an authoritative source. Every claim about behavior is backed by an experiment you can run.

Frozen stack: Docker Engine 29.10.0 · containerd 2.4.2 · runc 1.5.3 · BuildKit 0.35.0 · Linux 7.0.14 · Go 1.27.4.

The course

Section titled “The course”

Fifteen weeks, bottom to top: the kernel primitives first, then the standard built on them, then the network, the engine, and hardening. Weeks 13–15 go beyond Docker and finish your own engine. Each module answers one question. Full curriculum →

I · Foundations

What the kernel gives a process, and how containers differ from VMs.

  1. 01Processes and the kernel boundaryWhat is a process, what does the kernel give it, and why is PID 1 special?week 1in review
  2. 02Containers are not VMsWhat separates a container from a virtual machine, and where did containers come from?week 1planned

II · Isolation primitives

The kernel features a container is made of: namespaces, cgroups and union filesystems.

  1. 03Namespaces I: the filesystem view and identityHow does a process get its own view of the filesystem, hostname, IPC and PIDs?week 2planned
  2. 04Namespaces II: users, network, cgroup and time; capabilitiesHow can root inside a container be nobody outside, and what does 'privileged' really mean?week 3planned
  3. 05cgroups v2How is a group of processes limited, measured and killed as one unit?week 4planned
  4. 06Union filesystems and snapshottersHow can a hundred containers share one image on disk and still each write freely?week 5planned

III · The container standard

Turn the primitives into an OCI runtime, and learn what an image actually is.

  1. 07The OCI runtime, and Project 1: miniruncWhat exactly is a container as a standard, and what must a runtime do?week 6planned
  2. 08Images and distributionWhat is an image, byte for byte, and how does it get from a registry onto disk?week 7planned

IV · Networking

From a lone network namespace to published ports, service discovery and multi-host overlays.

  1. 09From a network namespace to -p 8080:80How does a packet get from outside into a process in a network namespace, and back out?week 8planned
  2. 10libnetwork, DNS and multi-hostHow do containers find each other by name, and talk across hosts?week 9planned

V · The engine

How dockerd, containerd, the shim and runc cooperate, and how BuildKit builds images.

  1. 11One docker run, end to endWhat happens, process by process and call by call, between pressing Enter and your app's first instruction?week 10planned
  2. 12Builds: Dockerfile to LLB to image, and Project 2What does docker build actually compute, and why does caching work the way it does?week 11planned

VI · Hardening and operations

What stands between a container and the host, and how state, lifecycle and plugins work.

  1. 13SecurityWhat actually stands between a container and the host, and how does it fail?week 12planned
  2. 14Storage, lifecycle and pluginsWhere does container state live, who restarts containers, and how does Docker load plugins?week 13planned

VII · Beyond Docker

Other runtimes, contributing upstream, and your own engine.

  1. 15Alternative runtimes and contributingWhat else can sit where runc sits, and how do you get a change into moby?week 14planned
  2. 16Capstone: budCan you run, network, build and secure containers with an engine you wrote?week 15planned
