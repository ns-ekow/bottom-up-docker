## Question

What does it take for a process to start in its own PID namespace?

## Concept

`unshare(2)` with `CLONE_NEWPID` does not move the caller itself into a new PID namespace. The
caller's first child after the call becomes the first process in it <Claim src="man:unshare.2#description" />.
That first process has PID 1 inside the namespace and acts as its init <Claim src="man:unshare.2#description; man:pid_namespaces.7#description" />.

## Read: how runc joins namespaces that already exist

Creating new namespaces is only half the job: sometimes runc must *join* namespaces that already
exist, and it does that in C, before the Go runtime starts <Claim src="runc-docs:libcontainer/nsenter/README.md#nsenter" />.

<Walkthrough src="runc@46365c6:libcontainer/nsenter/nsexec.c#L543-L585" title="__join_namespaces: setns into each namespace" mark="560">
  <Note lines="543-547">
    The function's contract: *try* to join every namespace in the `allow` set, skipping any that fail with a permission error, and return the set it actually joined <Claim src="runc@46365c6:libcontainer/nsenter/nsexec.c#L543-L548" />.
  </Note>
  <Note lines="557-558">
    A namespace outside `allow` is skipped before `setns(2)` is ever called for it <Claim src="runc@46365c6:libcontainer/nsenter/nsexec.c#L552-L560" />.
  </Note>
  <Note lines="560-563">
    The join is a single `setns(2)` on a file descriptor that refers to the target namespace, and every attempt is logged at debug level <Claim src="runc@46365c6:libcontainer/nsenter/nsexec.c#L560-L563; man:setns.2#description" />.
  </Note>
  <Note lines="564-569">
    `EPERM` skips that namespace. Any other error aborts <Claim src="runc@46365c6:libcontainer/nsenter/nsexec.c#L564-L569" />.
  </Note>
  <Note lines="579-582">
    After joining a user namespace, runc switches to root inside it, matching what `unshare(CLONE_NEWUSER)` does <Claim src="runc@46365c6:libcontainer/nsenter/nsexec.c#L572-L582" />.
  </Note>
</Walkthrough>
